# P3. Запирание без отключения: отчёт

Дата: 2026-11-07. Windows 10 Enterprise LTSC 2021, WinFsp 2.1, крейт `winfsp` 0.13.2.

## Что сделано

`gatefs/`: passthrough из P1 плюс модуль `src/gate.rs`, то есть два состояния без отключения:
- **заперто**: корень пустой, любой путь «не найден», создать файл нельзя; файлы, открытые до запирания, получают «отказано в доступе» на любую операцию, кроме закрытия;
- **открыто**: обычный passthrough;
- у каждого открытого файла есть номер поколения; запирание увеличивает поколение, поэтому файл, открытый до запирания, остаётся мёртвым и после открытия папки. Так и будет в Zamok: после запирания ключ стёрт, старые дескрипторы восстановить нечем;
- файловая система запоминает, какой процесс какой файл открыл (`FspFileSystemOperationProcessIdF`), и при запирании пишет список;
- после переключения она шлёт Проводнику `SHChangeNotify(SHCNE_UPDATEDIR)`;
- переключение в прототипе идёт через файл управления (`P3_CONTROL`), в Zamok это будет команда по именованному каналу.

`test-p3.ps1`: окно Проводника открыто на папке, отдельный процесс PowerShell держит файл открытым, как Word, а дальше идут запирание, проверки, открытие, проверки и повторное подключение.

## Результаты

**16 из 16** при выключенном кэше сведений о файлах (`FileInfoTimeout = 0`), два прогона подряд. С кэшем в 1 секунду 14–15 из 16, причина ниже.

| Вопрос | Ответ |
|---|---|
| Нужно ли отключать папку, чтобы запереть | Нет. Точка подключения и процесс живут, меняется только поведение |
| Сколько длится запирание | Около 0,5 с вместе с ожиданием прототипа (опрос файла управления раз в 100 мс) |
| Окно Проводника, открытое на папке | Переживает запирание и после обновления показывает пустую папку. После открытия снова показывает файлы. Ошибки «диск занят» нет: у Cryptomator эта проблема решается отключением, а мы ничего не отключаем |
| Файл, открытый другой программой до запирания | Чтение и запись после запирания: «Отказано в доступе». После открытия папки этот дескриптор так и остаётся мёртвым, программе нужно открыть файл заново |
| Не попала ли запись из мёртвого дескриптора в файл | Нет, исходный файл не изменился |
| Кто держал файлы | Список верный: `powershell.exe  6656  \a.txt`. Значит, предупреждение «Word держит Отчёт.docx» из DESIGN.md (п. 2.3) делается средствами самой файловой системы, без Restart Manager |
| Создание файлов в запертой папке | Отказано |
| Атрибут «системный» на точке подключения после повторного подключения | **Пропадает.** WinFsp создаёт точку подключения заново при каждом подключении, поэтому Zamok должен ставить атрибут сам после каждого подключения, иначе пропадёт иконка замка |

## Главная находка: кэш ядра показывает запертое ещё до секунды

С `FileInfoTimeout = 1000` сразу после запирания файл, открытый другой программой, ещё виден по имени (`Test-Path` возвращает «есть»), а однажды не сразу опустел листинг корня. Через 1,5 секунды всё правильно. С `FileInfoTimeout = 0` всё правильно сразу.

Причина: ядро WinFsp держит сведения о файле (имя, размер, время, атрибуты) и листинги каталогов в своём кэше и не спрашивает нашу программу, пока кэш не истёк. **Содержимое при этом не утекает**: чтение через старый дескриптор отказало сразу. Утекают на долю секунды только сведения о файле.

Что это значит для Zamok:
- запирание должно сбрасывать кэш ядра через `FspFileSystemNotify` по всем путям, сведения о которых могли попасть в кэш. Файловая система знает эти пути: она сама отвечала на запросы о них в пределах `FileInfoTimeout`;
- запасной вариант: считать папку запертой, только когда истёк `FileInfoTimeout`, и до этого держать окно «Запираю…»;
- это прямо конфликтует со скоростью (DESIGN.md, раздел 7: там длинный кэш предлагался как главный ускоритель). Значение `FileInfoTimeout` выбираем в P5 с учётом этой находки, сброс кэша при запирании нужен в любом случае.

## Не проверено

- Настоящий Word и VS Code вместо процесса PowerShell. Поведение то же на уровне файловой системы, но программы по-разному переживают «отказано в доступе». Проверить вручную: открыть документ, запереть, посмотреть, что скажет Word.
- Ярлык `.lnk` внутри папки: у Cryptomator он мешал отключению, у нас отключения нет, поэтому проблемы быть не должно. Отдельно не проверялось.
- Сброс кэша через `FspFileSystemNotify`: в прототипе не сделан, проверить на этапе 3.

## Вывод

Запирание без отключения работает: Проводник и программы с открытыми файлами не мешают запереть, старые дескрипторы умирают, список «кто держит файлы» есть. Устройство из DESIGN.md (п. 3.2) подтверждается с одной поправкой: запирание обязано сбрасывать кэш ядра.
