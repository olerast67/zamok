# Проверки файловой системы (этап 3)

- `test-fs.ps1`: 33 проверки на настоящей подключённой зашифрованной папке. Каждое изменение повторяется в обычной папке-зеркале, в конце хранилище читается библиотеками Cryptomator и сравнивается с зеркалом. Нужны собранные `zamok-mount` (`cargo build --release -p zamok-fs`) и JDK 26 для Cryptomator (см. `tests/fixtures-tool/README.md`).
- `test-load.ps1`: нагрузочная проверка, одна папка на 100 000 файлов через настоящее подключение (раздел ниже). Нужна release-сборка `zamok-mount`. Параметр `-Count` уменьшает число файлов для быстрой пробы.
- `bench-fs.ps1`: замеры на тех же задачах, что в прототипе P5. Результаты в `bench-results.md`.

Разброс между прогонами большой (Defender, фоновая работа), сравнивать стоит порядки.

Что дало ускорение:
- кэш расшифрованного содержимого каталогов: поиск имени, в том числе несуществующего и без учёта регистра, больше не расшифровывает все имена каталога;
- при создании и удалении кэш дополняется, а не сбрасывается;
- заголовок файла читается и расшифровывается только при первом чтении или записи, а не при каждом открытии ради сведений о файле.

- кэш сведений о файлах в ядре WinFsp (`FileInfoTimeout` = 1 с); при запирании он сбрасывается уведомлениями по всем путям, которые ядро могло закэшировать, и «заперто» сообщается только после этого (проверка «открытый файл не виден сразу после запирания» проходит).

Что осталось (этап 9): просмотр дерева медленнее NTFS примерно в 5 раз, `git status` в 8 раз; цель из DESIGN.md — не больше чем в 4 раза.

## Файл, отображённый в память, и запирание (`test-mmap.ps1`)

Скрипт запускает `zamok-core` со своей папкой данных и своим каналом, как `tests/core/test-core.ps1`. Две программы-помощника (`mapper.exe`, собирается скриптом) отображают файл 1 МиБ из открытой папки только для чтения и сразу закрывают дескрипторы файла и секции: остаётся одно отображение, так держат документы некоторые программы. Программа A читает начало файла, программа B ничего не читает. Потом папку запирают командой `lock`.

Результат 2026-11-10 (12 из 12):

| Что | Что происходит |
|---|---|
| Одно отображение без открытого дескриптора | считается открытым файлом, статус называет программу (`open_in`: `mapper.exe`) |
| Запирание по бездействию | ждёт, пока отображение есть |
| Запирание вручную | не отказывает: папка запирается, ключи стёрты |
| Страница, которую A прочитала до запирания | A читает её и после запирания, открытый текст |
| Та же страница в отображении B, которое её не трогало | B тоже читает открытый текст: страница лежит в общем кэше Windows |
| Страница, которую до запирания не читал никто | не загружается, программа получает ошибку страницы (`SEHException`; программа без обработки этой ошибки аварийно завершается) |
| Новое открытие файла | запрещено |
| Программа с отображением завершилась | счётчик открытых файлов остаётся 1 без имени программы ещё минимум 5 секунд: Windows держит секцию файла в кэше и закрывает файл в WinFsp позже |

Для модели угроз: запирание защищает от новых чтений, но не стирает то, что уже загружено в память. Страницы файла, прочитанные до запирания, остаются в общем кэше Windows, и любая программа, у которой этот файл был отображён до запирания, читает их и после. Программа, которая отобразит файл после запирания, этого сделать не может: открытие запрещено. Описано в DESIGN.md, раздел 6.

## Папка на 100 000 файлов (`test-load.ps1`)

Прогон 2026-11-09, release-сборка `zamok-mount`, один каталог, файлы по 1 КиБ, содержимое зависит от номера файла, хранилище 107 МБ в `tests/tmp/load`, в конце всё удаляется.

| Шаг | Время | Результат |
|---|---|---|
| Создать 100 000 файлов | 805 с (124 файла/с) | |
| Перечислить | 4,2 с | 100 000 имён |
| Открыть и прочитать 3000 файлов | 17,6 с | 0 неверных |
| Запереть | 0,13 с | файл не виден |
| Открыть | 0,08 с | |
| Перечислить после открытия (имена расшифровываются заново) | 5,6 с | 100 000 имён |
| Проверить содержимое 3000 файлов | 16,8 с | 0 неверных |
| Удалить все файлы | 52,6 с (1901 файл/с) | |

Память `zamok-mount`, частная / рабочий набор: пустая папка 2 / 8 МБ, после создания 68 / 72 МБ, после чтения 76 / 80 МБ, запертая 18 / 25 МБ, после открытия и проверки 61 / 65 МБ, пик рабочего набора 108 МБ.

Что нашёл тест: `read_directory` собирал весь список заново на каждую порцию ответа, время на большом каталоге росло квадратично. На 2000 файлах просмотр занимал 3,7 с, после исправления 0,1 с. Создание остаётся медленным (около 8 мс на файл): время одинаково на 2000 и 100 000 файлах, то есть от размера каталога не зависит. Его разбор в этапе 9.
