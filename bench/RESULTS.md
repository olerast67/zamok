# Замеры скорости (этап 9)

Дата: 2026-11-09. Код: коммит, в котором лежит этот файл (ветка `speed`). Машина: Windows 10 Enterprise LTSC 2021, Intel Core i5-11300H (8 логических ядер), 16 ГБ, NVMe Intel H10 (QLC плюс Optane), Microsoft Defender включён и не менялся. Рядом работал обычный zamok-core автора (простаивал).

Запуск: `powershell -NoProfile -ExecutionPolicy Bypass -File bench\run-bench.ps1 -PassthroughExe <p3-gatefs.exe>`. Задачи как в P5: 20 000 файлов по 1–8 КБ в 2000 папках, файл 1 ГБ. Три прогона каждого варианта со сменой порядка, в таблицах медиана (минимум–максимум). Перед каждым замером скрипт ждёт затихания MsMpEng и System, не дольше 30 с. WinFsp без шифрования: прототип P3, `FileInfoTimeout` 1000 мс, собран из текущего кода репозитория.

Параллельная расшифровка больших запросов (запрос `copy /b` это 1 МиБ, то есть 32 куска), чтение 1 ГБ, пять прогонов, две пары: без неё 2,08 и 1,92 с, с ней 1,53 и 1,48 с.

Убрано, так как выигрыша нет: открытие шифротекста вне общего замка таблицы файлов. Распаковка 12,16 против базовых 11,3–12,3. Сравнение итоговой версии с ним и без него: 9,82 и 8,33 с ним, 9,66 и 9,42 без него. Разница меньше шума, а логика сложнее (заголовок пустого файла нельзя писать из двух потоков).

Не трогали: `FileInfoTimeout` остаётся 1 с (P5 показал почти нулевой выигрыш от большего значения, а запирание важнее); scrypt работает только при открытии папки, на файл его нет; `fsync` по-прежнему только на явный flush; параллельное шифрование записи не делали, цель по записи выполнена без него.

## Разброс и Defender

- Сразу после создания исходных данных ожидание затихания упиралось в потолок 30 с перед каждым замером, дальше укладывалось в 2,6 с. Причина разброса в начале прогонов это хвост фоновой работы: Defender проверяет только что созданные файлы, ОС дописывает кэш на диск.
- Выбросы при записи 1 ГБ (22, 26 и 38 с вместо 4–6) с Defender не связаны: MsMpEng потратил в этих замерах меньше 0,2 с процессора, System 0,6–1,7 с. Запись ждала диск, похоже на исчерпание быстрого кэша NVMe H10 (QLC). Такие же выбросы есть у NTFS (P5, здесь 6,29). Отсюда разброс в разы, который видели раньше.
- Доля Defender: исключение из проверки это настройка безопасности, менять её нельзя, поэтому прогона без Defender нет. Измерено процессорное время MsMpEng.exe во время замера. Распаковка дерева: NTFS 5 с, passthrough 284 с, Zamok 240 с (при 45 с настоящего времени, примерно 5 ядер из 8). `git add + commit`: 35, 253 и 251 с. На листинге и `git status` Defender почти не виден. Почти вся нагрузка при создании файлов приходится на проверку Defender и общая для любой файловой системы на WinFsp.

## Формат 8 для папок с кодом

Цели выполнены, `git status` на границе. Чтение большого файла дошло до цели после упреждающего чтения (раздел ниже). Формат не упирается в себя: Zamok быстрее passthrough без шифрования на создании файлов и на git, значит, оставшееся время тратится в WinFsp и Defender, а второй формат их не убирает. Решение записано в `docs/DESIGN.md`, раздел 11.

## Упреждающее чтение большого файла (2026-11-10)

Код: ветка `read-ahead-repro`. Машина та же, Defender включён. Рядом работали другие сессии разработки, поэтому абсолютные числа выше, чем 2026-11-09, а сравнение «до» и «после» сделано в одно время.

Запуск тем же сценарием, только копирование и чтение 1 ГБ, пять прогонов, медиана (минимум–максимум):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File bench\run-bench.ps1 -Runs 5 -Files 40 -Variants ntfs,zamok `
    -Skip 'unpack tree,list tree,git add+commit,git status,delete tree' -MountExe <zamok-mount.exe> -KeepSeed
```

| Вариант | Копирование 1 ГБ | Чтение 1 ГБ | Чтение, доля от NTFS |
|---|---|---|---|
| NTFS (прогон «до») | 2,60 (2,57–40,6) | 0,73 (0,71–0,86) | |
| Zamok до (main, `8ad59a2`) | 5,09 (4,85–37,1) | 2,08 (2,01–2,39) | 35% |
| NTFS (прогон «после») | 2,60 (2,59–20,8) | 0,74 (0,72–0,76) | |
| Zamok после | 5,22 (4,54–5,70) | 1,00 (0,86–1,32) | 74% |

Худший прогон «после» (1,32 с) даёт 56%, тоже выше цели. Вариант WinFsp без шифрования в этот раз не запускался.

Где было время. `copy /b` читает запросами по 1 МиБ строго по очереди, второй запрос не приходит, пока не отдан первый. Сам Zamok без WinFsp (`cargo run --release -p zamok-fs --example read_speed`, 512 МиБ из кэша ОС) читал 0,65–0,68 с на 512 МиБ, после правок 0,32–0,36 с. Внутри WinFsp запрос занимал 0,6–1,0 мс, и всё это время ядро ждало.

Что сделано, по шагам:

1. Куски расшифровываются прямо в буфер ответа (`decrypt_in_place_detached` из RustCrypto, при неверном теге буфер обнуляется), без промежуточного вектора на каждый кусок и второй копии.
2. Шифр AES-GCM с развёрнутым ключом файла строится один раз при открытии, а не на каждый кусок.
3. Общий пул из четырёх потоков (rayon) вместо создания потоков на каждый запрос, буфер шифротекста не выделяется заново на каждый запрос. Шаги 1–3 вместе: чтение через WinFsp 1,21 с против 1,87 с у main в том же чередующемся замере (восемь чтений каждого, файл 1 ГБ).
4. Упреждение: после большого запроса, идущего подряд за предыдущим, пул сразу читает и расшифровывает следующий запрос такого же размера, пока ядро отдаёт текущий. Следующий запрос забирает готовые данные одним копированием. Запись, изменение размера и запирание отменяют упреждение; чтение не подряд его не заказывает. В том же чередующемся замере 0,87 с.
