# 02. Формат хранения, криптография, производительность

Дата исследования: 2026-11-07. Лимит поиска был жёсткий (10 загрузок), поэтому часть фактов помечена НЕ ПРОВЕРЕНО: перед архитектурным решением такие пункты нужно сверить с первоисточником.

## 1. Cryptomator vault format 8

Проверено (источники: https://docs.cryptomator.org/security/architecture/ и https://docs.cryptomator.org/security/vault/):

- Конфиг `vault.cryptomator` (JWT): `format: 8`, `cipherCombo: SIV_GCM` (альтернатива `SIV_CTRMAC`), `shorteningThreshold: 220`.
- KDF: scrypt, в примере cost N=32768, r=8, без параллелизма, выход 32 байта (KEK). Соль лежит в `masterkey.cryptomator`.
- `masterkey.cryptomator`: два 32-байтных ключа (encryption и MAC) обёрнуты AES Key Wrap (RFC 3394) под KEK. Есть `versionMac` (HMAC-SHA256 от версии) против даунгрейда. JWT конфига подписывается объединённым мастер-ключом.
- Имена: UTF-8 NFC, AES-SIV, associated data = dirId родителя (перенос файла между папками детектируется), затем base64url и суффикс `.c9r`.
- Каталоги: dirId корня = пустая строка, остальные случайные ASCII до 36 символов (UUID). Путь `d/XX/YYYY...` = Base32(SHA-1(AES-SIV(dirId))), разбит 2+30 символов. Все зашифрованные каталоги лежат плоско. Папка внутри каталога представлена файлом `dir.c9r` (содержит dirId), симлинк это `symlink.c9r`. Опциональный `dirid.c9r` нужен для восстановления.
- Длинные имена: если имя с `.c9r` длиннее 220 символов, узел хранится как `base64url(sha1(имя)).c9s/` с файлами `name.c9s` и `contents.c9r`. Порог 220 оставляет запас под суффиксы конфликтов облаков.
- Содержимое: заголовок 68 байт (nonce 12, AES-GCM payload 40 [8 байт 0xFF и 32 байта ключа файла], tag 16). Чанки по 32 KiB открытого текста, у каждого nonce 12 и tag 16, то есть до 32 KiB + 28 байт. AES-GCM, AAD = номер чанка (64-bit BE) и nonce заголовка. Накладные расходы около 0,09 %, но минимум 68 байт на любой файл.

Утечки метаданных (вывод из структуры, отдельного раздела в документации нет): количество узлов и их типы (файл, папка, симлинк); размер файлов с точностью до чанка (паддинга нет, он был убран в v1.2.0, см. https://nuetzlich.net/gocryptfs/comparison/); примерная длина имён; факт имени длиннее 220; времена изменения файлов. Идентичные имена в одной папке дают одинаковый шифртекст (SIV детерминирован). Плоская схема `d/` скрывает иерархию, но не число узлов в каталоге.

НЕ ПРОВЕРЕНО: результаты независимого аудита. Был аудит Cure53 (2017) для 1.x; по формату 8 свежего аудита не нашёл. Проверить на https://cryptomator.org/audits/.

Достаточность спеки для независимой реализации: да, формат хорошо описан в docs.cryptomator.org, референс на Java это `cryptomator/cryptolib` (лицензия, вероятно Apache-2.0, НЕ ПРОВЕРЕНО). Не хватило на загруженных страницах точной формы JWT и KDF-полей, их придётся сверять с cryptolib.

Независимые реализации (по результатам поиска, зрелость НЕ ПРОВЕРЕНА):
- Rust: `cryptomator-rs-crypto` v0.1.2 (дек. 2025), github.com/Dar9586/cryptomator-rs. Поддерживаемые форматы из листинга не ясны (https://rust-digger.code-maven.com/crates/cryptomator-rs-crypto).
- C#/.NET: SecureFolderFS возможно совместим с Cryptomator (см. п.2, НЕ ПРОВЕРЕНО). Отдельной .NET-библиотеки не нашёл.
- C++: не нашёл.
- Тестовые векторы: публичного набора не нашёл (НЕ ПРОВЕРЕНО, смотреть тесты cryptolib). Практичный путь: создать несколько vault'ов настоящим Cryptomator и использовать как fixtures.

## 2. gocryptfs, cppcryptfs, SecureFolderFS

gocryptfs (https://nuetzlich.net/gocryptfs/comparison/): содержимое AES-GCM с целостностью, имена EME (wide-block), scrypt, свой IV на каталог, иерархия каталогов сохраняется (не плоская), размеры не скрываются. Размер блока на странице не указан (по памяти 4 KiB, НЕ ПРОВЕРЕНО). Только Linux/macOS CLI. Замечание на странице про "CTR без целостности" у Cryptomator относится к старым версиям, формат 8 использует GCM.

cppcryptfs: Windows-реализация gocryptfs на Dokany, тестировалась как совместимая с gocryptfs 1.4. Лицензия и статус обслуживания НЕ ПРОВЕРЕНЫ.

SecureFolderFS (https://github.com/SecureFolderFS-Community/SecureFolderFS): лицензия MIT, .NET с Uno Platform / WinUI / MAUI, десктоп (Windows, macOS, Linux) и мобильные клиенты, есть SDK и CLI, 287 звёзд и 294 коммита на момент загрузки. Свой формат, поддержка Cryptomator-vault'ов и использование WinFsp/Dokany на странице репозитория не упомянуты, проверить в коде. Это ближайший проект по стеку: стоит прочитать код и рассмотреть участие вместо написания с нуля.

Экосистема: у Cryptomator самая богатая (официальные iOS и Android, Windows/macOS/Linux, Cyberduck, WebDAV). У gocryptfs Linux/macOS и Windows через cppcryptfs, мобильные только сторонние (НЕ ПРОВЕРЕНО).

Мелкие файлы: решает реализация, а не формат. Бенчмарк gocryptfs (Windows 7, i7-6700, NVMe, 2019, данные старые) распаковка linux-3.0: NTFS 26 с, cppcryptfs 456 с, securefs 332 с, Cryptomator 2497 с (тогда не WinFsp). Все шифрованные FS были CPU-bound на мелких файлах.

## 3. Производительность на Windows

- cppcryptfs, https://github.com/bailey27/cppcryptfs/issues/10: 29 289 файлов (1,68 GB, с .git) шли 12 файлов/с и 0,74 MB/s. Автор винит Dokany (задержка между user-mode DLL и драйвером): cppcryptfs ведёт себя как mirror-пример Dokany. Эпоха Dokany 1.x.
- Cryptomator: мейнтейнер пишет, что node_modules медленный из-за числа мелких файлов, воспроизведено на ~18k файлов по 6 KiB (issues https://github.com/cryptomator/cryptomator/issues/3170, /451, /3384, содержимое НЕ ПРОВЕРЕНО построчно). Пользователи винят Defender и Windows Search Indexer; исключение процесса и пути помогало не всегда. Сообщество рекомендует WinFsp.
- WinFsp (https://winfsp.dev/doc/WinFsp-Performance-Testing/): in-memory FS быстрее NTFS в большинстве тестов, оверхед драйвера небольшой. Слабые места: повторные open (каждый open требует round-trip в user mode) и листинг одного файла (слабое directory-кэширование). Тесты последовательные, это худший случай; параллельная нагрузка выигрывает за счёт батчинга контекст-свитчей.
- Узкие места (вывод): открытие файла = чтение и расшифровка заголовка плюс SIV имени; листинг = расшифровка всех имён на каждый вызов; много мелких файлов = много round-trip user/kernel; JVM у Cryptomator добавляет накладные расходы.
- Приёмы быстрой FS (из общих знаний о WinFsp, `FileInfoTimeout` на загруженных страницах не упомянут, значения и поведение проверять в WinFsp docs и замером): кэширование метаданных ядром (`FileInfoTimeout` в параметрах тома, большое значение допустимо, если том меняется только нами), cached I/O вместо no-buffering, кэш расшифрованных имён и листингов (LRU), кэш dirId, чанк 32 KiB как единица кэша данных, многопоточный диспетчер и параллельное шифрование, AES-NI, write-back для грязных чанков, минимум вызовов к NTFS на операцию.
- Defender: исключения требуют прав администратора и на виртуальных томах помогают не всегда (отчёты пользователей). Для node_modules стоит предусмотреть явную опцию "хранить вне шифрованного тома" (junction на обычную папку) как осознанный компромисс безопасности с предупреждением.

## 4. Windows Hello

Проверено: Cryptomator 1.17.0 (июнь 2025) добавил разблокировку через Windows Hello (лицо, отпечаток, PIN) и разблокировку двойным кликом по `vault.cryptomator`, интеграцию написал purejava (https://cryptomator.org/blog/2025/06/25/desktop-1.17.0/). Пользователи упоминают локальный файл `windowsHelloKeychain.json` с сохранённым паролем (https://community.cryptomator.org/t/cryptomator-1-17-0-windows-say-hello/16558). Там же отчёт, что после 1.17 vault'ы в OneDrive стали read-only (НЕ ПРОВЕРЕНО, связь с обновлением не доказана).

НЕ ПРОВЕРЕНО (в загруженных документах нет, читать код purejava и `cryptomator/integrations-win`): точный API (KeyCredentialManager или DPAPI), использование TPM, обработка recovery key.

Схема для win-lock независимо от Cryptomator: KEK или пароль оборачивается ключом, который создаёт `KeyCredentialManager.RequestCreateAsync` (подпись challenge, ключ в TPM, каждый раз жест Hello), либо DPAPI. Компромисс: DPAPI расшифровывается любым процессом пользователя без запроса Hello; KeyCredential требует подтверждения на каждую подпись, но тогда ключ-обёртку надо получать из детерминированной подписи. Hello должен только кэшировать доступ, пароль и recovery key остаются главным способом восстановления.

## 5. Облачная синхронизация

Формат Cryptomator проектировался под синхронизацию: каждый узел отдельный файл, имена с запасом до 255 символов (порог 220), плоское дерево. Проблемы (https://community.cryptomator.org/t/onedrive-created-another-copy-of-a-cryptomator-file/13078, https://community.cryptomator.org/t/advice-to-resolve-file-conflict-in-vault/636, https://community.cryptomator.org/t/dropbox-stuck-in-sync-ejecting-drive-failed/224):
- OneDrive создаёт копии с именем ПК перед `.c9r`; Cryptomator помечает конфликт суффиксом "(Conflict ...)", разбор ручной.
- Мультиклиентской блокировки нет: одновременная правка с двух машин даёт конфликт.
- Dropbox зависает, "eject" не проходит, обычно из-за процессов, держащих файлы.
- Самое опасное (вывод): конфликт `dir.c9r` и `masterkey.cryptomator`/`vault.cryptomator`, а также синхронизация во время записи.
- Яндекс.Диск и Google Drive: целевых отчётов не нашёл (НЕ ПРОВЕРЕНО).
Для режима "шифрование на месте" хранилище лучше держать вне синхронизируемых каталогов или ставить синхронизацию на паузу при открытой папке.

## Рекомендация

Формат. Два пути:
1. Совместимость с Cryptomator vault format 8: плюсы публичная спека, аудит, мобильные приложения, доступ с Linux/macOS, готовые fixtures. Минусы: на каждый узел отдельные файловые операции, 68 байт заголовка и dir.c9r на каждую папку, размеры не скрыты.
2. Свой формат, оптимизированный под много мелких файлов (по типу gocryptfs/securefs: иерархия сохраняется, один индекс на папку, пакеты мелких файлов). Быстрее, но без экосистемы.
Рекомендую начать с формата 8 как основного режима и сразу ввести абстракцию `VaultFormat`, чтобы позже добавить быстрый собственный формат для папок, которым не нужны мобильные клиенты. Своей криптографии не писать: AES-SIV, AES-GCM, scrypt из проверенных библиотек.

Язык и библиотеки. Rust для горячего пути: крейт `windows` (KeyCredentialManager, DPAPI), WinFsp через C API или `winfsp-rs` (зрелость НЕ ПРОВЕРЕНА), крипто RustCrypto (`aes-siv`, `aes-gcm`, `scrypt`, `aes-kw`), за основу можно взять `cryptomator-rs-crypto` (проверить качество) и сверять с `cryptolib`. Интерфейс на C#/WinUI поверх Rust-ядра, если нужен нативный вид. Перед выбором сделать прототип на два дня: passthrough mirror FS на WinFsp и замер `git clone` и `npm install`, чтобы знать пол накладных расходов WinFsp на этой машине.

Меры по производительности с первого дня:
- бенчмарк-набор в репозитории: распаковка linux-подобного дерева, `git status`, `git clone`, `npm install`, поиск по дереву, копирование 1 GB; сравнение с голым NTFS и passthrough WinFsp;
- LRU-кэши расшифрованных имён, листингов каталогов и dirId, инвалидация только своими операциями записи;
- метаданный кэш ядра WinFsp (`FileInfoTimeout`) и cached I/O, значения подбирать замером;
- многопоточный диспетчер и параллельное шифрование чанков, AES-NI;
- кэш открытых хэндлов и заголовков файлов, write-back для чанков;
- политика Defender (инструкция исключений, замер с ним и без), опция junction для node_modules с предупреждением;
- минимум обращений к NTFS на одну операцию.

Проверить до начала разработки: полная спека и тесты `cryptomator/cryptolib`; код purejava для Windows Hello; код SecureFolderFS (совместимость с Cryptomator, использование WinFsp); аудит формата 8.
